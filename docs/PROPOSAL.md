## 一、选题定位

**在正确的时间，为正确的人，预约一份「刚刚好、更划算」的餐。**

（按时段求解营养目标 → 自动匹配当前订单可用券 → 提示预约时段内正在进行的活动）

一个基于麦当劳 MCP 能力的 WorkBuddy Skill：输入一句自然语言（时间、人数、各自的营养目标、预算），输出一份可直接确认下单的**预约方案卡片**——包含推荐的餐品组合、营养核算、达成度评分、以及为什么选这个时间点的解释。

### 它不是一个营养查询工具

| | 营养查询工具 | 本 Skill |
|---|---|---|
| 输入 | 我想吃什么 | 我几点吃、和谁吃、要达成什么目标 |
| 输出 | 一份营养表 | 一个含时间决策的预约方案 |
| 核心逻辑 | 查表 | **四维约束求解** |

## 二、核心洞察：时间 ↔ 营养 是双向约束

这是本方案的技术护城河，已通过 MCP 实测证实。

### 2.1 麦当劳的菜单按预约时间动态返回

`query-meals` 的入参包含 `reservationDate`（格式 `yyyy-MM-dd HH:mm`）。实测同一门店：

- 传 `2026-10-12 08:00` → 返回**早餐菜单**：麦满分系列、厚松饼堡系列、早安营养卷、炒双蛋堡系列、一早现磨
- **巨无霸、麦辣鸡腿堡、板烧鸡腿堡等正餐产品完全不在返回列表中**

### 2.2 门店返回分餐段的可预约时段

`query-nearby-stores` 在 `reservation=true` 时返回 `reservationTimeOptions`。实测北京朝阳区某门店：

```
早餐(06:14至10:15)，午餐(10:44至14:15)，下午茶(14:44至16:45)，夜市(17:14至21:45)
```

另一门店（东大桥）额外多一个餐段：`宵夜(22:14至22:46)`。

**餐段之间存在约 29 分钟的空档**（10:15→10:44、14:15→14:44、16:45→17:14），这是厨房切换设备的窗口。

### 2.3 由此产生的双向约束

```
正向：预约时间 → 决定可点餐段菜单 → 决定营养可行域
反向：营养目标 → 反推最优餐段 → 推荐预约时间
```

**这就是「营养 + 预约」不是功能叠加、而是真正咬合的原因。**

举个实测数据支撑的真实例子：

| 餐品 | kcal | 蛋白 | 钠 |
|---|---|---|---|
| 巨无霸（正餐） | 513 | 27g | 961mg |
| 双层猪柳蛋麦满分（早餐） | 513 | **29g** | 1210mg |

同样是 513 kcal，早餐蛋白更高但钠也更高。**如果你要「高蛋白 + 控钠」，应该约午餐；如果只要「高蛋白 + 控卡」，约早餐更划算。**

这就是这个 Skill 存在的意义——**普通人不可能自己算出这个权衡**。

## 三、为什么值得做（意义）

### 3.1 三个真实存在的断层

**断层一：营养信息看得见，用不上。**
麦当劳公开了 160 项餐品的完整营养数据，但没有人会在点餐前拿计算器把「汉堡 + 薯条 + 可乐」的钠加一遍。数据在那里，决策却不在。

**断层二：时间和菜单是耦合的，但用户不知道。**
用户说「明天中午 12 点」，他不知道这个时间点锁死了正餐菜单，进而锁死了营养可行域。反过来，「我想吃高蛋白早餐」这个诉求本身就隐含了「必须在 10:15 前」。

**断层三：多人场景完全无解。**
「我和两个同事吃饭，我在控卡、他在增肌」——现有工具要么帮你算一个人，要么什么都不算。整单的多目标营养核算，目前没有产品做。

### 3.2 对麦当劳的业务价值

- **预约转化率**：把「我要预约」升级为「我知道该预约什么、该约几点」
- **客单结构优化**：替换优化（可乐换无糖、小薯换玉米杯）在不降低客单的前提下提升健康感知
- **差异化心智**：在快餐行业里，第一个把「营养目标」变成「可执行的预约决策」的品牌

### 3.3 对开发者的价值

展示了一个真实命题：**MCP 给的是原子能力，价值在于编排。**
单个 `list-nutrition-foods` 只能查表；把它和 `query-meals`（带时间参数）、`query-meal-detail`（拆套餐）、`calculate-price`（算价）串起来，才能产生用户每天愿意用的闭环。

## 四、目标用户与场景

### 核心用户

1. **有明确饮食管理目标的职场人**（控卡、控钠、控糖、增肌）
2. **需要帮团队订餐的人**（团餐、部门聚餐，成员目标各异）
3. **规律健身人群**（对蛋白/热量有硬指标）

### 典型场景

**场景 A｜单人 + 时间已定**
> 明天中午 12 点在公司楼下吃，帮我控制在 600 kcal 以内

**场景 B｜单人 + 目标优先，时间待定**（杀手功能）
> 我想吃够 30g 蛋白又不想超过 600 kcal，帮我看看明天约几点合适

**场景 C｜多人 + 目标各异**（杀手功能）
> 明天中午我和两个同事吃饭，我在减脂（<600kcal）、小王增肌（蛋白>40g）、小李随便，预算 120

**场景 D｜已有偏好，求优化**
> 我平时都点巨无霸三件套，有没有更健康点的替换方案

## 五、功能设计

### 5.1 五维约束求解模型

| 维度 | 数据来源 | 说明 |
|---|---|---|
| **时间** | `query-nearby-stores` 的 `reservationTimeOptions`、`businessStart/EndTime` | 餐段可选性 + 门店营业时间 |
| **菜单** | `query-meals`（传 `reservationDate`） | 该时段的实时可售菜单 |
| **营养** | `list-nutrition-foods` + `query-meal-detail` | 拆套餐 → 累加单品 |
| **预算** | `query-store-coupons` → `calculate-price` | 取当前订单可用券 → 算价 |
| **活动** | `campaign-calendar`（传 `specifiedDate`） | 活动窗口 × 预约时间交叉提示 |

### 5.2 MVP（必须完成）

- [x] 自然语言解析：抽取时间、人数、营养目标、预算（`scripts/parse_request.py`）
- [x] 门店查询与餐段匹配（`resolve_store.py`，含换餐空档检测）
- [x] 按时段拉取实时菜单（`query-meals` 传 `reservationDate`）
- [x] 营养数据解析与套餐拆解累加（`parse_nutrition.py` + `plan_meal.decompose`）
- [x] 约束过滤 + 达成度排序，输出 Top3 方案（`plan_meal.plan`）
- [x] 方案卡片渲染（营养 + 价格 + 理由 + 券 + 活动）（`render_card.py`）
- [x] **确认后才调用 `create-order`**（写死在 SKILL.md 护栏里）

### 5.3 进阶

- [x] **反向时段推荐**：给营养目标反推最佳预约时间（`recommend_slot.py`）
- [x] **多人目标求交**：整单多目标核算（`plan_meal.plan_group`）
- [x] **替换优化**：基于 `query-meal-detail` 的可替换项微调（`optimize_replacements.py`）
- [x] **券与活动联动**（`apply_benefits.py`）——`auto-bind-coupons` 保持「需显式同意」，不自动调用
- [ ] 历史订单营养复盘（`order-list` + `query-order`）——**明确不纳入**，见下

> **为什么不做历史订单复盘**：它与「时间 ↔ 营养」的核心命题无关，属于功能堆砌。
> 每多一个不咬合「时间」的功能，就稀释一分记忆点——而记忆点才是 Star 的来源。

### 5.4 进阶功能（第二轮，同样由实测驱动）

判断标准不变：**只做能跟「时间」咬合的能力**。四个进阶项各自都推翻或坐实了一个直觉假设。

| 进阶功能 | 咬合点 | 实测依据 |
|---|---|---|
| **① 多门店择优** `compare_stores.py` | 「门店」本身就是一个时间约束：不同门店的**可预约餐段**不同 | 相距 236 m 的两店，东大桥有「宵夜(22:14–22:46)」而朝外没有 → 22:30 在最近的店**无解** |
| **② 时间紧迫度** `time_guard.py` | 已结束的餐段**不会出现在返回里**，必须与另一天做差集 | 今天(12:39)列表无早餐，明天有 → 「现在想吃麦满分」必须被告知改约明天 |
| **③ 多日排程** `plan_week.py` | 差异不来自菜单，而来自每天的可约餐段 + 当天活动数 + 跨天不重样 | **推翻假设**：相邻两天菜单完全一致；但活动数为 12 / 2 / 1 |
| **④ 无解诊断** `diagnose.py` | 「没有方案」不是答案，要指出卡在哪、放宽到多少有解 | 「能量≤400 且 蛋白≥30」→ 蛋白质下探到 23g（调整 23.3%）即可完全达标 |

**④ 的算法要点**：放宽量是**精确计算**而非网格搜索。对目标 `k`，只扫描满足其余全部目标的候选，取 `k` 字段的极值（max 目标取最小、min 目标取最大）——这个值按构造就是仍有解的最紧目标。

**① 的诚实边界**：同商圈门店菜单重合度约 95%，宽松目标下各家最优餐品通常相同。所以代码与文案都写明：门店择优的真实价值在「该时间哪家可约」与「某款餐品哪家还有」，不夸大。

### 6.2 MCP 调用链路（实测确认）

```
now-time-info
  └─ 获取当前服务器时间与时区

query-nearby-stores (beType=1, searchType=2, city, keyword)
  └─ 返回 storeCode / businessStartTime / businessEndTime / reservation
     └─ reservation=true 时返回 reservationTimeOptions（分餐段可约时段）

query-meals (storeCode, orderType=1, beType=1, reservationDate="yyyy-MM-dd HH:mm")
  └─ 返回 categories[]（分类 + code + tags）与 meals{code: {name, image, currentPrice, originalPrice, discountType}}

query-meal-detail (code)
  └─ 拆分套餐组成与可替换项（关键：菜单多为组合套餐，营养表为单品）

list-nutrition-foods
  └─ 返回 160 条文本表格，需解析

query-store-coupons (storeCode)
  └─ 返回「当前门店 + 当前订单」实际可用的券
     ✅ MCP 已代做门店/渠道/配送方式校验，无需自行推算券期

calculate-price (含优惠券)
  └─ 计算应付总价

create-order（仅用户显式确认后调用）
```

> ⚠️ **修正**：原计划把「券的有效时段」当作一个需要自行求解的时间约束。实测 `available-coupons` 只返回**标题、状态、图片**，**不含有效期字段**。
> 正确做法是改用 `query-store-coupons(storeCode)`，让 MCP 完成可用性校验——**更准确，也更省事**。

### 6.3 关键工程点

**① 营养数据需要文本解析（实测确认）**

`list-nutrition-foods` 返回的 `data` 是**字符串而非 JSON**：

```
[160]{productName,nutritionDescription,energyKj,energyKcal,protein,fat,carbohydrate,sodium,calcium}:
  猪柳麦满分,null,1288,308,16,16,24,781,213
  巨无霸,null,2146,513,27,26,42,961,171
```

需写解析器：跳过表头 → 按逗号切分 → 处理 `null` → 转成结构化字典。

**② 菜单与营养表需要名称对齐（最大风险，实测已发现缺口）**

`query-meals` 返回的是**组合套餐**（如「巨无霸三件套」「猪柳蛋麦满分套餐」），而 `list-nutrition-foods` 是**单品**。两者无法直接匹配，必须：

```
菜单套餐 code → query-meal-detail 拆出单品（rounds[].choices[] 中 isDefault=1 且 quantity>0）
      → 各单品匹配营养表（精确 → 模糊）
      → 累加整单营养
```

**`query-meal-detail` 返回结构（实测确认）**：`data.rounds[]` 是选配轮次，每轮含 `choices[]`；choice 的 `isDefault=1` 且 `quantity>0` 即为该套餐默认带出的单品，其余 choice 是**可替换项**并带 `diffPrice`（如 中薯条 → 小杯玉米杯 `- ¥1.5`）。`scripts/plan_meal.py::decompose()` 即按此规则抽取 `defaultItems` 与 `replacements`。

实测还发现确有缺口（如菜单里的「吉士蛋麦满分」在营养表中无对应项）。降级策略：

- 名称精确匹配 → 失败则模糊匹配（去空格/括号/规格词）
- 仍失败 → 该单品标记为「暂无官方营养数据」，方案标注「不完整」，**绝不编造数值**
- 若核心主餐缺失 → 该方案不进入推荐列表

**③ 求解算法**

规模可控（单品约 160，一顿 2-4 件），用**枚举 + 剪枝 + 打分排序**即可，无需复杂优化器：

```
1. 按餐段拿菜单，按 categories 归类（主餐/小食/饮品）
2. 枚举组合：主餐 × 小食(0-1) × 饮品(0-1)
3. 用 query-meal-detail 拆套餐并累加营养
4. 硬约束过滤：热量区间、钠上限、蛋白下限、预算上限
5. 软目标打分：Σ w_k · 达成度_k，取 Top3
6. 对 Top1 用可替换项做微调优化
```

**④ 安全设计（重要）**

- 所有下单动作必须用户显式确认，**任何情况下不自动 `create-order`**
- 不自动 `auto-bind-coupons`（避免未经同意的账户操作）
- 热量设下限保护，**不支持极端低卡目标**
- 措辞统一为「均衡膳食」「营养搭配」，**不使用「减肥」「节食」「断食」**——赛事内容合规条款明确禁止「宣扬不健康饮食方式」

**⑤ 活动只做交叉提示，不做活动浏览器**

实测 `campaign-calendar` 返回的活动带**明确时间窗口**：起止日期（「10月8日至10月21日」）与精确到分钟的开售时刻（「10:30 正式开售」）。这与「预约时间」天然耦合。

正确用法：当推荐的预约时间落在某活动窗口内时，在方案卡片里追加一行提示。

**不要**做成活动列表/日历浏览器——那会让 README 失去焦点，且和官方示例「活动推荐助手」撞车。

### 7.6 反向时段推荐实测结果（杀手功能）

输入「我想吃够 25g 蛋白又不想超过 600 kcal，钠也别超过 800 毫克，帮我看看明天约几点合适」，
对同一门店（1950121）2026-10-12 的三个餐段分别求解：

| 餐段 | 最佳组合 | 能量 | 蛋白 | 钠 | 价格 | 评分 |
|---|---|---|---|---|---|---|
| **早餐 (06:14–10:15)** | **猪柳炒双蛋堡** | 437 kcal | **25 g** | 705 mg | ¥18 | **3.00** |
| 午餐 (10:44–14:15) | 培根蔬萃双层牛堡 | 442 kcal | 24 g | 728 mg | ¥25 | 2.96 |
| 下午茶 (14:44–16:45) | 培根蔬萃双层牛堡 | 442 kcal | 24 g | 728 mg | ¥25 | 2.96 |

**结论：建议预约 06:14（早餐时段）。** 早餐餐段三项目标全部达成，正餐餐段蛋白质只到 96%。

这条结果同时验证了两件事：一是早餐与正餐是两套互不相交的菜单（早餐菜单无巨无霸，正餐菜单无麦满分）；
二是「时间 × 营养」的反向约束可被真实数据求解，不是概念包装。

### 7.7 `query-store-coupons` 实测（修正了原假设）

原方案假设「券无有效期，需自行推算」——**实测推翻了一半**：

- `available-coupons`：只有标题/状态/图片，**无有效期**，确实无法推算。
- `query-store-coupons`：额外返回 `tradeDateTime`（有效期）与 `products[].productCode`（适用商品编码）。

且该 `productCode` 与 `query-meals` 的餐品编码**同属一个编码空间**，
于是「券 → 方案」可做**确定性匹配**而非模糊比对。演示账号实测 `data` 为空数组，
已作为降级场景固化进 `tests/fixtures/coupons_real_empty.json`。

**但券接口不返回优惠面额**，因此券后价必须由 `calculate-price` 给出，本项目不估算。

### 7.8 `campaign-calendar` 按日分组（实测确认）

传 `specifiedDate=2026-10-12` 返回三天数据，活动数量差异极大：

| 日期 | 活动数 |
|---|---|
| 2026-10-11 | 12 |
| 2026-10-12 | 2 |
| 2026-10-13 | 1 |

**「约哪一天」真的会改变能赶上哪些活动。** 实现上必须以按日分组为第一判据
（如 `麦当劳 X PEACEMINUSONE` 在 10-12 那一组里没有，即使其窗口从 10-08 起也不适用）。

### 7.9 `query-meals` 的门店维度 vs 日期维度（实测，两个方向结论相反）

为排除混淆，采集了三组全量返回做交叉对比：1950121@10-12、1950121@10-13、1950006@10-12（均为午餐 12:00）。

| 对比轴 | 结论 |
|---|---|
| **门店**（同日期同时段，1950121 vs 1950006） | 菜单**不同**，差异 6 vs 11 项 |
| **日期**（同门店同餐段，10-12 vs 10-13） | 菜单**完全一致** |

门店差异项中被官方营养表**精确收录**的部分：

- 东大桥（1950006）独有：**脆脆薯条**（279 kcal / 钠 540 mg / 钙 13 mg）
- 朝外（1950121）独有：**抹茶阿芙佳朵**（147/50/136）、**咖啡阿芙佳朵**（139/49/111）、**浓缩咖啡**（13/0/7）

比菜单更锋利的是**餐段差异**：东大桥有 `宵夜(22:14至22:46)`，朝外没有。这使「晚上 22:30 想约」成为只有一家店能解的命题——**门店本身就是一个时间约束**。

### 7.10 已结束的餐段不会出现在返回里（实测）

门店 1950121 的 `reservationTimeOptions`：

| 日期 | 解析出的餐段 |
|---|---|
| 2026-10-11（采集时刻 12:39） | 午餐(10:44–14:15)、下午茶(14:44–16:45)、夜市(17:14–21:45) |
| 2026-10-12 | **早餐(06:14–10:15)**、午餐、下午茶、夜市 |

早餐段**直接不在今天的列表里**。推论：

1. 「今天还能否约早餐」不能从今天的返回直接读出，必须与另一天做差集；
2. 今天 08:00 会因为早餐段缺失被 `match_segment` 判为 `closed`，但正确结论是 `elapsed`（时间已过）——这是自测中修掉的一个真实 bug。

### 7.11 无解诊断实测（场景 E4）

目标：「能量 ≤ 400 kcal 且 蛋白 ≥ 30 g」，午餐餐段。

| 阶段 | 数量 |
|---|---|
| 可点单元 | 17 |
| 有完整官方营养数据 | 12 |
| 通过硬约束筛选 | **8** |
| 完全达标 | **0** |

诊断输出：

| 约束 | 要求 | 放宽到 | 调整幅度 | 对应方案 |
|---|---|---|---|---|
| 蛋白质 | ≥ 30 g | **23 g** | 23.3% | 板烧鸡腿堡 ¥23.5 |
| 能量 | ≤ 400 kcal | — | — | 即使完全放开，其余目标仍无法同时成立 |

关键点：**「无解」不是零方案，而是零个完全达标的方案**。硬约束只挡掉 9 个，剩下 8 个都能点，只是没有同时满足两个目标的。诊断模块区分这两种失败，避免对用户撒谎。

### 7.12 多日排程实测（场景 E5）

目标：每天「能量 ≤ 700 kcal 且 钠 ≤ 800 mg」，连续三天不重样。

| 日期 | 推荐组合 | 能量 | 蛋白 | 钠 | 价格 | 当天活动 |
|---|---|---|---|---|---|---|
| 10-12 | 麦香鸡 | 369 kcal | 15 g | 731 mg | ¥17 | 2 个 |
| 10-13 | 麦香鱼 | 325 kcal | 16 g | 556 mg | ¥23 | 1 个 |
| 10-14 | 培根蔬萃双层牛堡 | 442 kcal | 24 g | 728 mg | ¥25 | 0 个 |

## 十、冲 Star 策略

排名只看 Star，所以 README 就是产品本身：

1. **首屏一句话讲清「时间 ↔ 营养」的双向约束**——这是别人没有的角度
2. **放真实数据对比**：巨无霸 vs 双层猪柳蛋麦满分，同样 513 kcal 的蛋白/钠权衡
3. **动图演示反向推荐**：输入营养目标 → 输出「建议约 10:44 后」
4. **`nutritionDescription` 字段是宝藏**：麦当劳官方给的生活化类比（「能量约鲈鱼 1 条」「能量约猕猴桃 2 个」）极具传播力
5. **诚实标注数据边界**：「暂无官方营养数据」的降级设计反而是专业性的体现
6. **「实测推翻直觉」是最强的内容钩子**（进阶功能带来的新素材）：
   - 相距 236 m 的两家麦当劳，晚上 22:30 一家能约、一家不能约
   - 同一家店相邻两天的**菜单完全一致**，但可约餐段和活动数完全不同
   - 「_INTERFACE 不会返回已结束的餐段」，所以「今天约不到早餐」必须靠差集才能发现
   - 「能量 ≤ 400 且蛋白 ≥ 30」无解，但蛋白质**只需下探到 23g** 就有解
   这几条都是反直觉、易验证、且与「时间」强相关的，适合做首屏与社媒传播。
